# Paired visual evaluation — NOT_RUN

This recipe is not evidence that the new guidance improves aesthetics. Run on an actual authorized
host with rendered previews. Keep artifacts in the consumer/evaluation project, not this instruction bundle.

Use the two briefs in docs/ui-design.md (source documentation): a three-section setup landing page
and an existing dense administration console. Supply identical content, brand/token baseline,
reference assets, model/settings, host tools, viewport sizes and comparable iteration budgets.
Record exact baseline/candidate commits, prompts and actual skills/providers used. Use fresh contexts
to reduce carry-over; compare multiple runs when feasible, and do not generalize from one pair.

For each version retain screenshots, runnable artifact references, tested revision, interaction logs,
remaining findings and environment limitations. A reviewer should compare blinded A/B labels where
practical and score each dimension 1–5 with a concrete observation:

- Requirement/content fidelity (extra sections or fabricated claims are failures).
- Hierarchy/readability, spacing rhythm and appropriate information density.
- Brand fit and coherent differentiation, without rewarding novelty for its own sake.
- Responsive behavior, long text and important state coverage.
- Actual interaction, keyboard/focus and reduced-motion behavior.

Record preference and reasons separately from functional/accessibility findings. Fix critical usability
issues before visual acceptance; automated tests alone cannot assign aesthetic scores. Record who
reviewed and whether business-owner acceptance exists. Missing browser/provider = NOT_RUN/BLOCKED,
not a zero-quality result or invented PASS. Compare old/new on the same brief before claiming improvement.
